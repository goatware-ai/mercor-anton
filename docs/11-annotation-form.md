### 2 · Architecture, Modularity & Trade-off Soundness (A)

`field_ta_dim2_score_a` · likert_scale · **required** · min_value 1.0 · max_value 5.0

Options: `🔴 Must redo`, `🟠 Substantial rework`, `🟡 Light rework needed`, `🟢 Minor polish only`, `🟣 Production ready`

**Dimension 2: Architecture, Modularity & Trade-off Soundness**

Evaluates structural design, abstraction level, and qualitative engineering trade-offs. Labelers must calibrate expectations based on the task context: prioritize modularity and maintainability for architectural features, or surgical precision and minimal scope for bug fixes. The agent should demonstrate judgment in choosing the appropriate scoping and complexity for the specific goal.

**🟣 5: Production ready**

* Demonstrates senior-level engineering judgment and domain-appropriate architecture.
* Makes sound qualitative and algorithmic trade-offs (e.g., O(1) hash lookup vs O(n²) nested loop; streaming large datasets vs loading into memory).
* Chooses clean extensibility over ad-hoc wiring or short-term hacks.
* Modularity is well-balanced—avoids both unmaintainable hacks for production code and over-abstracted enterprise hierarchies for simple MVPs.
* Proactively selects the optimal strategy for the task's scope (e.g., minimal invasive changes for bug fixes vs. robust, extensible design for new features).

**🟢 4: Minor polish only**

* Demonstrates solid architectural design and appropriate data structure selection.
* Fulfills qualitative architectural requirements cleanly.
* Exhibits only minor, inconsequential design imperfections.

**🟡 3: Light rework needed**

* Functional and logically sound solution.
* Chooses a suboptimal trade-off (e.g., slightly ad-hoc wiring where an existing pattern would be cleaner).
* Uses a generic data structure (e.g., list) where a specialized one (e.g., set/map) would be more efficient.
* Fulfills the functional requirement, but the architectural strategy is slightly misaligned (e.g., overly complex for a small fix, or too simplistic for a structural change).

**🟠 2: Substantial rework**

* Exhibits poor abstraction, excessive coupling, or spaghetti code.
* Implements naive O(n²) nested loops in performance-critical paths.
* Chooses an ad-hoc hack that damages codebase maintainability when a clean solution was accessible.
* Architecture is fundamentally mismatched to the task's needs (e.g., over-engineering a simple patch with unnecessary abstractions, or introducing excessive coupling/hacks in a core feature).

**🔴 1: Must redo**

* Introduces severely broken or irrational architecture.
* Introduces circular dependencies or severe anti-patterns.
* Exhibits massive over-engineering (e.g., building a multi-layer inheritance tree for a quick MVP script).
* Architecture is fundamentally mismatched to the task's needs (e.g., over-engineering a simple patch with unnecessary abstractions, or introducing excessive coupling/hacks in a core feature).

### 3 · Codebase Conventions & Utility Reuse (A)

`field_ta_dim3_score_a` · likert_scale · **required** · min_value 1.0 · max_value 5.0

Options: `🔴 Must redo`, `🟠 Substantial rework`, `🟡 Light rework needed`, `🟢 Minor polish only`, `🟣 Production ready`

**Dimension 3: Codebase Conventions & Utility Reuse (Anti-Duplication)**

Evaluates adherence to project idioms, naming, style, active utility reuse, and diff cleanliness (avoiding duplication, over-editing, and under-editing).

**🟣 5: Production ready**

* New code is indistinguishable from surrounding senior maintainer code and adheres strictly to project idioms and naming.
* Proactively discovers and reuses existing helpers, constants, ORMs, test fixtures, and error-handling hierarchies with zero duplicate logic.
